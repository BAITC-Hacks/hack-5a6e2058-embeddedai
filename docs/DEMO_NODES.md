# Три узла для предметного разбора

Карточки ниже вычислены из официальных `data/data/*.parquet`, правила **2.2**,
период **1–31 июля 2026**. Источник чисел — `artifacts/result.json`, создаваемый
[одной командой](../README.md). Контрольный размер: 2248 узлов, 3119 рёбер,
4840 переводов. Актуальные SHA-256 исходников находятся в
[run_report.json](../artifacts/run_report.json); выгрузки —
[nodes_roles.csv](../artifacts/nodes_roles.csv), [clusters.csv](../artifacts/clusters.csv)
и [top_nodes.csv](../artifacts/top_nodes.csv).

Это примеры для закрытого показа жюри, не зашитые ответы алгоритма. Они выбраны
из результата по прозрачному правилу: первый по рангу coordinator, первый по
рангу transit и первый по рангу узел с `boundary_censored=true`. На другом наборе
или при изменении правил нужно выбрать и пересчитать примеры заново.
Официальные карточки не следует размещать на публичном демонстрационном VPS.

## Быстрый поиск и независимые карточки

В локальном интерфейсе вставлять gid **как текст целиком** в «Найти узел по gid»,
нажимать ↗, затем «Показать окружение узла». Последовательно показать:

| gid | Что объяснить | Где искать в текущей очереди |
|---|---|---|
| `100000003684369100` | Связующий узел; порядок правил и неполный вход seed | TOP, место 1 |
| `100000003635170100` | Объёмный транзит и отличие от временной последовательности | TOP, место 28 |
| `100000003220685100` | Почему граница графа не считается конечным получателем | Поиск gid; место 389 |

Без сервера, браузера и AI получить эти три карточки одной командой из корня
(одинаково в PowerShell, Bash и zsh):

```text
uv run --frozen --no-dev python scripts/demo_nodes.py --result artifacts/result.json --gid 100000003684369100 --gid 100000003635170100 --gid 100000003220685100 --out output/submission/node_cards
```

Скрипт проверяет сохранённый результат, находит **переданные**, а не заранее
заданные gid и создаёт отдельный `.md` для каждого: метрики, все пороги,
совпавшие правила, поправки, пути, ограничения, следующие проверки и SHA-256.
Для трёх произвольных gid жюри заменить три значения; без `--out` карточки
печатаются в терминал. Неизвестный gid возвращает код 2 до записи карточек.
Основной пайплайн повторно запускать не требуется.

## 1. Связующий узел — `100000003684369100`

**Гипотеза:** связывает несколько наблюдаемых ветвей сети. Основная роль
`coordinator`, `role_score=0.693865`, `priority_score=0.986876`, место **1**,
сообщество **2**. Это seed (`depth=0`), не граница и не изолят.

| Признак | Значение | Порог coordinator |
|---|---:|---:|
| Seed-предков | 6 | ≥ 2 |
| Различных плательщиков | 24 | ≥ 3 |
| Различных получателей | 62 | ≥ 2 |
| P(betweenness) | 0.970784641 | ≥ 0.90 |
| Вход от других клиентов | 3 848 436.00 KZT | В формуле роли абсолютного денежного минимума нет |
| Выход другим клиентам | 8 588 655.00 KZT | В формуле роли абсолютного денежного минимума нет |
| Входящих / исходящих операций | 58 / 67 | — |

Все четыре условия выполнены. При `S(x,t)=min(max(x/t,0),1)` поддержка:

```text
0.35*S(6,4) + 0.30*0.970784641 + 0.20*S(24,6) + 0.15*S(62,5)
= 0.991235392…
поправка seed: × 0.7 → 0.693865 после округления
```

**Почему не distributor?** Это правило тоже выполнено: 62 получателя и
67 исходящих операций превышают порог 10. Его поддержка после поправки
`0.697050`, даже немного выше. Основная роль выбирается по задокументированному
порядку `coordinator → distributor → transit → consolidator → terminal → peripheral`,
**не** по максимальному score. В карточке сохраняются обе роли и оба расчёта.
Роли, основанные на отношении потоков, для seed не назначаются из-за неполного входа.

**Что показать:** входящее ребро `100000008748914100 → 100000003684369100`:
1 582 700.00 KZT, 9 переводов; исходящее
`100000003684369100 → 100000001072022100`: 740 000.00 KZT, 2 перевода.
Сообщество 2 содержит 138 узлов, 3 seed, внутренний оборот 18 838 290.00 KZT.

**Ограничение:** выход/вход ≈ 2.231726 не означает создание денег или нарушение:
входы извне выборки неизвестны. Следующие запросы — история входов seed,
межбанковские переводы и операции ниже порога выгрузки. При 12 изменениях весов
±20% место остаётся 1, но это устойчивость очереди, не точность определения роли.

## 2. Объёмный транзит — `100000003635170100`

**Гипотеза:** сопоставимые входящий и исходящий объёмы. Роль `transit`,
`role_score=0.860335`, `priority_score=0.880174`, место **28**, сообщество **11**,
`depth=1`. Не seed и не граница.

| Признак | Значение | Проверка |
|---|---:|---|
| Вход / выход | 268 500.00 / 253 500.00 KZT | Оба положительны |
| Отношение выход/вход | 0.944134078 | В интервале [0.8; 1.2] |
| Плательщики / получатели | 3 / 4 | Входящие и исходящие связи присутствуют |
| Входящих / исходящих операций | 13 / 10 | `S(min(13,10),3)=1` |
| Seed-предков | 5 | Не достаточно само по себе для coordinator |
| P(betweenness) | 0.830550918 | Ниже порога coordinator 0.90 |

```text
role_score = (1 − abs(0.944134078 − 1)/0.4) * (0.5 + 0.5*S(10,3))
           = 0.860335 после округления; коэффициент наблюдаемости = 1
```

**Почему не другая роль?** Coordinator исключён из-за посредничества ниже
90-го процентиля, distributor — из-за 4 получателей при минимуме 10.
Для consolidator отношение 0.944134 превышает 0.2; terminal не подходит,
поскольку есть исходящие связи. Выполнено только правило transit.

**Что показать:** есть взаимная пара с `100000004209339100`:
вход в разбираемый узел — 232 500.00 KZT, 10 операций; обратное направление —
138 500.00 KZT, 6 операций. Это наблюдаемый короткий цикл в агрегированном графе,
не доказанный возврат одних и тех же средств.

**Временная проверка:** возможно сопоставить за следующие 1–2 дня только
64 000.00 KZT, то есть **23.8361%** входа. Пересечение входа и выхода в один день
100 500.00 KZT показано отдельно и не прибавляется к этой сумме. Сопоставимость
месячных объёмов не доказывает быстрый транзит. Нужны точное время операций,
остатки и внешние поступления. Место при изменениях весов: **21–31**.

## 3. Отказ от необоснованной роли — `100000003220685100`

**Гипотеза:** наблюдений недостаточно. Роль `peripheral`, `role_score=0`,
но `priority_score=0.557861`, место **389**, сообщество **10**. `depth=4`,
`boundary_censored=true`, не seed. Малая поддержка роли не означает безопасность.

| Признак | Значение | Значение для вывода |
|---|---:|---|
| Плательщики / получатели | 1 / 0 | Исходящее продолжение обхода не видно |
| Вход / выход | 1 306 000.00 / 0.00 KZT | Наблюдаемый выход не равен известному остатку |
| Входящих / исходящих операций | 2 / 0 | Оба входа 15 июля |
| Seed-предков | 3 | Есть структурная связь с исходными ветвями |
| P(betweenness) | 0 | Сквозных путей через этот конечный наблюдаемый узел нет |

**Почему не terminal?** Условие `depth=4 и out_deg=0` помечает границу.
Для terminal и consolidator обязательно отсутствие этой цензуры; нулевой выход
здесь нельзя интерпретировать как удержание денег. Coordinator также не проходит
по числу плательщиков/получателей и посредничеству; distributor не проходит
по исходящим связям; transit — по наблюдаемости и отсутствию выхода.
Ни одно конкретное правило не выполнено, поэтому назначены peripheral и score 0.

**Что показать:** единственное входящее ребро
`100000003457710100 → 100000003220685100`: 1 306 000.00 KZT, 2 операции.
Пунктирная граница узла, предупреждение и следующий запрос в карточке:
**«Запросить следующий уровень исходящих переводов»**. Сообщество 10 содержит
126 узлов, 35 граничных узлов и 24 907 250.33 KZT внутреннего оборота.
В нём 0 seed: seed-предки могут находиться в других сообществах.

## Как объяснить три произвольных gid за минуту

Для каждого узла: **роль → 2–4 определяющие метрики с порогами → ранее стоящее
правило, которое не прошло, либо приоритет между совпадениями → поправка
наблюдаемости → одна следующая проверка**. Карточки скрипта и блок «Вклад в
приоритет и правила» содержат необходимые числа. Не называть role_score
вероятностью нарушения и не приравнивать priority_score к объёму денег.

Полные формулы и оговорки — [METHODOLOGY.md](METHODOLOGY.md), порядок пяти минут —
[DEMO.md](DEMO.md), один слайд архитектуры — [SOLUTION.svg](SOLUTION.svg).
