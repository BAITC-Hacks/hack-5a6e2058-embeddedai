# Масштабирование без подмены качества

Текущая версия — локальный воспроизводимый анализатор с ограничением загрузки
10 000 узлов, 50 000 рёбер и 100 000 транзакций. **Полный анализ миллиона узлов
не реализован и не проверен.** Ниже разделены работающие оптимизации, измерения
и архитектура следующего этапа. Повышение лимитов само по себе недостаточно.

## Что уже оптимизировано

- Построение графа и обработка транзакций обходят строки через `itertuples`,
  сохраняя int64 идентификаторы и порядок сложения. Промежуточные Python-словари
  для каждой строки всей таблицы больше не создаются.
- Граф для метрик копируется только при наличии самопереводов. Исходные рёбра
  остаются неизменными. Словари степеней формируются по одному, а не одновременно
  со словарями PageRank и betweenness.
- Временная сводка создаёт словарь дня и множества контрагентов только для нового
  `(gid, дата)`. Представление даты и её порядковый номер переиспользуются.
  FIFO, окно 1–2 дня, исключение самопереводов и порядок суммирования сохранены.
- Входящий и исходящий оборот сообществ вычисляются одним проходом по уже
  агрегированным межкластерным парам: `O(F + K)` вместо `O(F × K)`, где `F` —
  число пар сообществ, `K` — число сообществ. Порядок сложения внутри каждого
  итога сохранён.
- Если в проекции нет изолятов, Louvain получает исходную проекцию без
  дополнительного представления подграфа. Порядок вершин, веса и seed сохранены.

Правила v2.1, веса, положительные процентили с усреднением равных значений,
округление и tie-break по числовому gid **не изменены**. PageRank остаётся
взвешенным суммой; betweenness точный до 2500 вершин, выше — 128 исходных вершин
с seed=42; Louvain использует прежнюю проекцию и resolution=1.

Три CSV официального набора после оптимизаций побайтно совпали с опубликованными
`artifacts/`. У обоих синтетических наборов ниже SHA-256 всех трёх CSV также
совпали до/после и во всех трёх повторениях. Это проверка сохранения поведения,
а не доказательство истинности присвоенных ролей.

## Воспроизводимые измерения

```bash
uv run python scripts/benchmark.py --nodes 1000 10000 --repeat 3
# Если локально есть архив организатора:
uv run python scripts/benchmark.py --nodes 1000 10000 --data data/data --repeat 3 --output benchmark.json
```

Замер 2026-09-23: Linux x86_64, Python 3.12.3, Intel Core i5-8250U, 8 GB RAM.
Базовая версия: `d83fe86`. Каждый повтор — отдельный процесс. Время включает
чтение Parquet, полный анализ, валидацию результата и запись CSV/JSON; не включает
установку зависимостей, импорт Python и генерацию входа. Пиковый RSS включает
импорт и генерацию. Файловый кэш ОС не сбрасывался; ноутбук выполнял другие задачи.
Приведены медиана времени и максимальный RSS трёх запусков, **не SLA**.

| Набор | V / E / транзакции | Betweenness | Время до → после | Пиковый RSS до → после |
|---|---:|---|---:|---:|
| Официальный | 2248 / 3119 / 4840 | точный | 4,50 → 4,57 с | 201,0 → 200,2 MiB |
| Синтетический | 1000 / 3000 / 6000 | точный | 1,20 → 1,33 с | 187,8 → 187,3 MiB |
| Синтетический | 10000 / 30000 / 60000 | 128 исходных вершин | 8,58 → 8,17 с | 436,9 → 429,5 MiB |

Синтетика — направленный граф четырёх последовательных уровней, генератор
NumPy seed=42, три ребра на узел в среднем, две транзакции на ребро, суммы
от 5000 KZT, все non-seed достижимы. Это один профиль сети; он не моделирует
все реальные финансовые графы. На малых наборах общее ускорение не доказано:
разница сопоставима с шумом измерений. Сняты конкретные лишние аллокации и
квадратичная зависимость сводки сообществ.

Отдельные измерения изменённых функций, три повтора для времени; память —
дополнительный запуск под `tracemalloc` с входом, созданным до начала отслеживания:

| Этап и фиксированный вход | Медиана до → после | Пик Python-аллокаций до → после |
|---|---:|---:|
| Дневные сводки: 1000 узлов, 100 000 операций, 31 день | 1,190 → 0,547 с | 59,69 → 25,51 MiB |
| Обороты 5000 сообществ, 15 000 рёбер | 9,005 → 0,086 с | 10,29 → 10,80 MiB |

Для временного набора у строки `i`: `src=i%500`, `dst=500+i%500`, сумма
`5000+i%100`, день июля `1+i%31`. Во втором наборе каждый `gid=i` — своё
сообщество, рёбра в `i`, `(i+1)%5000`, `(i+2)%5000` несут соответственно
10, 20, 30. Полные возвращаемые структуры до/после равны. Эти микрозамеры
показывают выигрыш конкретных этапов; их ускорение нельзя переносить на весь
пайплайн. Дополнительные агрегаты сообществ занимают немного больше памяти,
зато устраняют повторный просмотр всех пар для каждого сообщества.

Профилирование официального анализа через `cProfile` показало около 65% времени
в точном betweenness. Его алгоритм и качество ради выигрыша во времени не менялись.
Тесты `tests/test_scaling.py` проверяют сохранение направлений, int64,
самопереводов, входного графа, дневных сумм и межкластерных потоков; тайминги
не превращены в нестабильные CI-пороги.

## Отдельный эксперимент: миллион узлов в CSR

```bash
uv run python scripts/benchmark.py --csr-probe --output csr-probe.json
```

Этот эксперимент действительно создаёт **1 000 000 вершин и 5 000 000 рёбер**
в SciPy CSR, строит обратную матрицу, считает входящие/исходящие суммы и выполняет
одну итерацию матрично-векторного умножения. Это регулярный циклический граф
с пятью исходящими рёбрами, без Parquet, временных данных, ролей, Louvain,
betweenness, ранжирования и UI. Он **не запускает полный продукт на миллионе
узлов** и не измеряет сходимость PageRank на финансовой сети.

Один фактический запуск: построение 0,076 с; обратный CSR 0,039 с; суммы 0,105 с;
один шаг умножения 0,011 с. Две CSR-структуры заняли **128 000 008 байт**;
пик процесса — **291,4 MiB**. Проверены число рёбер, степени и сохранение
единичной массы вектора. Эти показатели относятся только к указанным операциям.

CSR хранит веса, индексы столбцов и границы строк в отдельных массивах; он
подходит для обхода исходящих соседей и умножения на вектор. Обратное направление
требует CSC или второго CSR. Это основание для следующего движка, а не обещание
столько же памяти для всего приложения. [Документация SciPy CSR](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csr_array.html)

## Какие затраты остаются

Обозначения: `V` — вершины, `E` — рёбра, `T` — транзакции, `S` — seed,
`D` — число наблюдаемых календарных дней, `K` — сообщества, `F ≤ E` — пары
сообществ, `I` — итерации PageRank, `k=128` — исходные вершины приближения.

| Этап | Основная зависимость | Что важно при росте |
|---|---|---|
| Загрузка, сверка транзакций и рёбер | группировка/сортировка до `O(T log T)` | Сейчас таблицы целиком в памяти |
| Степени, суммы, проекция | `O(V+E)` | Python-объекты NetworkX значительно тяжелее массивов |
| PageRank | `O(I(V+E))` | Отдельно контролировать остаток, dangling nodes и остановку |
| Точный betweenness | до `O(V(V+E))` | На миллионе узлов практически другой вычислительный бюджет |
| Приближённый betweenness | до `O(k(V+E))` | Фиксированное `k` не гарантирует одинаковую ошибку при росте сети |
| Охват seed | сумма размеров `S` обходов в глубину 4 | Малый cutoff не ограничивает размер окрестности хаба |
| Дневные сводки | `O(T)` накопление + сортировка дней | Состояние до `O(V·D)` и множества уникальных контрагентов |
| Louvain | проходы по рёбрам на нескольких уровнях | Нет обещания фиксированного числа проходов |
| Сводки сообществ | `O(V+E+F+K)` после оптимизации | Не перечитывать все пары для каждого сообщества |
| Процентили, ранги, 12 сценариев | несколько сортировок `O(V log V)` | Равные значения и порядок gid должны совпадать |
| Экспорт и API | размер результата | Единый JSON со всеми карточками не подходит для миллиона |

**Важный численный предел:** NetworkX останавливает PageRank по критерию
`len(G) × tol`. При текущем стандартном `tol=1e-6` и миллионе вершин это порог
1 для ошибки итерации. Просто увеличить лимит загрузки означало бы получить
другую практическую точность. В будущем движке нужно версионировать явный
глобальный критерий остановки, хранить число итераций и остаток, затем проверить
изменение рангов. Сейчас параметры не менялись ради побайтной воспроизводимости.
[Документация NetworkX PageRank](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.link_analysis.pagerank_alg.pagerank.html)

Параметр `k` в NetworkX выбирает исходные вершины приближения betweenness;
все узлы остаются целями. Больший `k` улучшает приближение, но само по себе
значение 128 не задаёт доверительный интервал. Замена backend также требует
проверки нормировки и источника случайности.
[Документация NetworkX betweenness](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.centrality.betweenness_centrality.html)

## Архитектура для следующего этапа

```mermaid
flowchart LR
  P[Parquet: неизменяемый вход] --> B[Пакетная валидация и сверка]
  B --> C[Столбцы Arrow + dense ID ↔ int64 gid]
  C --> G[CSR исходящих и входящих связей]
  C --> T[Сортировка транзакций на диске по gid и дате]
  G --> M[Метрики в фоновом процессе]
  T --> M
  M --> R[Версионированные роли, ранги и CSV]
  R --> Q[Индекс карточек и окрестностей]
  Q --> U[API: страницы, сообщества, локальная схема]
```

1. **Вход и память.** Читать только нужные столбцы пакетами; проверять диапазоны
   int64, даты, нули, дубликаты, суммы/количество и BFS-согласованность. Группировки
   с большим состоянием выполнять через сортировку и промежуточные файлы.
   `ParquetFile.iter_batches` даёт пакеты, но один этот вызов не ограничивает память
   последующих группировок. `memory_map=True` не устраняет память на декодирование
   сжатого Parquet. [Пакетное чтение Arrow](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetFile.html),
   [память Parquet](https://arrow.apache.org/docs/python/parquet.html#reading-parquet-and-memory-mapping)
2. **Идентификаторы и суммы.** Отсортированный массив исходных signed int64 gid
   сопоставить плотным индексам `0..V−1`; в API по-прежнему отдавать строки.
   Не переводить gid во float. Переход денежных сумм к целым минимальным единицам
   разрешать только после проверки точности исходных значений и переполнения;
   произвольное округление входа изменяет данные.
3. **Граф.** Хранить направленные CSR/CSC и столбцовые атрибуты. Самопереводы
   сохранять отдельно; веса симметричной проекции получать сложением обоих
   направлений. Не разрезать граф произвольными блоками ради локального
   betweenness: пути между блоками изменят смысл метрики.
4. **Расчёты.** Степени и денежные агрегаты считать точно; PageRank — sparse
   умножениями с явной сходимостью. Для большого betweenness фиксировать список
   исходных вершин, проверять несколько выборок и увеличивать `k` до согласованной
   устойчивости. Пограничные кандидаты должны получать указание неопределённости,
   а не исчезать из анализа. Это будущая работа: сейчас применяется прежнее `k`.
5. **Кластеры.** Начать с того же Louvain на той же взвешенной проекции и проверить
   эквивалентность реализации. Изменение порядка вершин/seed может изменить
   результат; смена на другой алгоритм — новая методика, а не незаметная
   оптимизация. [Документация Louvain](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.community.louvain.louvain_communities.html)
6. **Хронология.** После сортировки по клиенту/дню считать одного клиента или
   ограниченную партицию за раз; FIFO хранит только двухдневное окно, но уникальные
   плательщики требуют точного группирования, а не вероятностного счётчика.
7. **Исполнение.** API создаёт фоновую задачу; отдельный процесс выполняет её с
   бюджетом памяти/времени, журналом этапов, отменой и контрольными точками.
   Вход, версия алгоритмов, конфигурация, seed и список pivots входят в ключ
   воспроизводимости. Результаты публикуются атомарно только после проверки.
8. **Просмотр.** Сохранять компактные таблицы и индекс по gid, не читать гигабайтный
   JSON при каждом запросе. TOP и список узлов — страницы; граф — сообщества и
   ограниченная окрестность с явными `matched/shown`. Полный экспорт выдавать
   потоково. Даже быстрый сервер не делает миллион элементов удобным экраном.

## Оценка памяти для V=1 млн, E=5 млн

Это расчёт размера примитивных массивов, **не измеренный RSS полного движка**.
Ниже MB — десятичные мегабайты. Для пяти миллионов позиций хватает int32;
после превышения диапазона индексов/указателей потребуются int64.

| Структура | Допущение | Размер |
|---|---|---:|
| Таблица исходных gid | `8·V` | 8 MB |
| Один CSR с весами | float64 веса + int32 индексы + int32 указатели: `12·E+4·(V+1)` | 64 MB |
| Два направления CSR | две такие структуры | 128 MB |
| Количество операций на ребре | один массив int64 | 40 MB |
| 20 числовых метрик узла | `20·8·V` | 160 MB |
| Три вектора PageRank | `3·8·V` | 24 MB |
| Флаги/роль/кластер | компактные целочисленные столбцы, пример бюджета | 16–32 MB |
| 31 млн дневных строк | условно 40 байт/строку без Python-объектов | 1240 MB |

Сюда не входят декодирование Parquet, сортировка, транзакции, проекция,
память Louvain/Brandes, индексы запросов, объяснения и экспорт. Например, 20 млн
транзакций при условных 24 байтах основных столбцов — ещё 480 MB до накладных
расходов. При дневной разреженности меньше 31 дня на узел объём сводок ниже.
Практический бюджет процесса должен иметь запас на временные массивы и
измеряться на реалистичной топологии; числа CSR нельзя использовать как бюджет
всего сервиса. Python-словари на каждый узел, ребро и день такой расчёт нарушают.

## План проверки качества перед включением большого режима

1. Сохранить текущий движок как эталон: официальный набор и малые графы с
   изолятами, seed, границей, циклами, петлями, одинаковыми оценками и MIN/MAX gid.
   Для оптимизаций представления требовать одинаковые CSV; метрики — одинаковые
   с оговорённым численным допуском, включая положительные процентили и rank ties.
2. На графах до 2500 вершин сверить новый betweenness с точным эталоном. На больших
   данных измерять ошибку доступных точных поднаборов, устойчивость TOP20/TOP100,
   изменение ролей и распределение по глубине; отдельно проверять трудные хабы.
   Exact на подграфе не выдавать за exact исходной сети.
3. Для PageRank контролировать массу, неотрицательность и остаток; для сообществ —
   внутренний оборот, modularity и совместное членство с учётом переименования
   кластеров. Проверять seed/границу и все обязательные строки при каждом запуске.
4. Нагрузочные наборы: цепочки, звёзды, множество компонент, плотные сообщества,
   крупный хаб, перекошенные суммы, повторные операции одного дня. Ступени:
   10k → 100k → 1M вершин; рёбра и транзакции масштабировать отдельно.
5. Измерять wall time, CPU, RSS, объём временного диска, API p95, отмену и
   восстановление после сбоя. Качество и ресурсы — два самостоятельных условия
   приёмки. Только после этих проверок увеличивать лимиты доступного пользователю
   режима и заявлять поддержку миллиона узлов.
